# Tatva CRM · Files module — notes for Claude

## What this is
An in-house web app for **Tatva by Tradeprop** (real estate: plots and weekend villas at Nal Village / Nalsarovar, near Ahmedabad; one project, "TATVA Villas & Plots", 415 plots). It replaces the company's Excel sheets for site visits, client holds/bookings/payments, plots, sold plots, the land partner (Anjanee Infraspace), contractors, site expenses and agent incentives. The owner is Vaibhav Pamnani (GitHub `Vpcodes11`). Reply to him in **English**, plainly; he is not a developer.

Live: https://tatva-crm.vaistack-cs.workers.dev — every push to `main` deploys automatically (Cloudflare Workers Builds, worker name `tatva-crm`, Cloudflare account vaistack.cs@gmail.com). There is no other deploy step.

## Stack (free Cloudflare plan)
- `public/index.html` — the whole website: one file, plain JS, no framework, no build. Hash routes (`#/visits`, `#/client/<id>`, …).
- `src/worker.js` — the server (Cloudflare Worker): JSON API under `/api/*`, sign-in, roles, and all writes.
- Cloudflare **D1** database `tatva-crm` (id in `wrangler.toml`). Tables are created automatically by `ensureSchema()` in the worker; `schema.sql` mirrors them.
- `data/` (not in git — client phone numbers): `seed.sql` / `tatva-data.json` = the original Excel data, only for local testing and the one-time import. The live data is in D1; **pushing code never touches it**.

## Data model
- Table `records(coll, id, sr, data JSON)` holds every business record. Collections: `visits, clients, bookings, payments, plots, expenses, landowners` (Dastavej register = "Sold plots" register), `advances, incentives, registry, dastavej, ledger` (contractor ledger lines), `contractors`, `notes` (client remarks), `plotOwners` (plot → client id), `meta` (summary).
- `edits` = every pencil change (old/new, who, when; used for Undo). `steps` = holds, bookings, payments, lapses, new visits/expenses, deletes. `trash` = deleted records (Super admin), restorable. `users`, `sessions`, `meta` (`version` counter for the "someone else made changes" notice; one-time migration flags).
- The browser loads everything with `GET /api/data` and writes with `POST /api/ops` (ops: `patch` a field, `put` a whole record, `del` to trash, `step` log). Multi-record actions (hold, book, pay, lapse, delete) change records in the browser, then send the changed records (`snap()` / `diffOps()` in index.html).

## Business rules (agreed with the owner — keep them)
- Roles: **Agent** (everything in Files except changing a Booked visit/booking), **Admin** (+ users, export), **Super admin** (+ delete/restore, other Super admins). The server enforces these, not only the screen.
- Flow: site visit → Hold (₹1,100 default, creates the client folder, plot = Hold) → Book (final amount, down payment; plot = Sold, visit = Booked, doc status "MOU not done") → payments → or Hold lapsed (plot back to Unsold, refund yes/no).
- **One source of truth**: a plot's status and owner come from its booking (Booked → Sold & owned; active hold → Hold). A visit linked to a client folder takes the folder's status (Booked → Booked, On hold → Hold, Lapsed → Lapsed); the one exception is a lapsed client's visit put back on Follow up (`reopened` on the visit; a new hold clears it). Lists, menu counts and modules must always agree — the owner checks this closely.
- **No "Converted" anywhere** (owner's rule, Nov 2026): the word is "Booked" on every page, choice, message and export. New bookings/visits save "Booked"; `migrateConvertedToBooked` renamed the saved values and edit history. Code still accepts old values (`isConvertedBooking`, `isConvertedVisitStatus` match Converted/DONE/Booked) — the function names are internal.
- Visit statuses: Follow up 1–4, Hold, Booked, Lapsed ("Not interested" was renamed Lapsed; old `NOT INTERESTED` values show as Lapsed). One Remark per visit (old follow-up notes were folded into it, "FU1 dd/mm/yy: … · FU2: …"). The saved text stays plain; `remarkHtml()` shows only the latest FU (label, short date, note) in the Site visits list (full text on hover), and every FU part on its own line on the visit page (FU3 = Sahil Bhai, FU4 = Pratik Sir). Visits can have several agents ("A, B").
- Clients list: newest first; Booked / On hold / Lapsed buttons. Site visits has two tabs: **Follow up** (every visit that isn't Lapsed; = the menu count) and **Lapsed** (visits marked Lapsed + visits of lapsed clients). Setting a visit to Lapsed moves it to the Lapsed tab; setting it to a Follow up moves it back. Each tab has its own Sr. series (1, 2, 3 … oldest first, worked out on screen by `visitSrs()`; the stored `sr` is unchanged), so a visit's Sr. changes when it moves tab.
- Client folder: top blocks Plot no., Plot size, Price per sq yd (= final amount ÷ size), Final amount, Paid till now, Remaining balance, Document status (a lapsed hold gives no final amount). Hold buttons are "Booked" / "Lapsed". Each plot card, rows of 3: left = Hold and booking (Hold date/amount/mode · Booking date/amount/mode · the booking payment's proof boxes for its mode (cheque: name / number / bank; the owner will link cheques to a module later) · DP date/amount/mode); right = MOU and dastavej (one block, one pencil; owner's layout Nov 27 2026: "MOU" Opted / Not opted on its own line + "Payment plan" Fixed payment / Variable payment; only when Opted, six boxes in rows of 3: MOU number, MOU date, MOU received till now / MOU remaining amount, MOU tenure, MOU EMI — all typed by the admin, saved on the booking as `mouOpted, mouPlan, mouNo, mouDate, mouReceived, mouRemaining, mouTenure, mouEmi`, separate from DP and NOT counted in Paid till now; then Dastavej delivery date / Date of dastavej / Name on dastavej from the dastavej record (`deliveryDate, date, client`). Old Dastavej status / Online-cheque / Cash are no longer shown (kept in data). `migrateMouOpted` marked old bookings whose MOU column mentions an MOU as Opted. MOU done = Opted with a date or number (`mouDone`); a dastavej record added in the CRM counts as done only once it has a date), then underneath "Refund and loan" (Refund switch/amount/mode · Loan/Loan amount/EMI; loan values "Loan Availed" / "Not Availed"). "+ Add payment" sits next to the Payments heading (the top of the folder has only "+ Hold another plot" / Delete folder). "How this folder was put together" is a closed line (`details.srcinfo`) at the bottom, under Payments; **no side column anywhere** (owner, repeated many times: never add a right-hand side box to any page); every page uses the full width. The folder's site visit date is in the header line, and its remark / FU follow-ups are rows in the folder's Remarks table. Refund only for a lapsed plot (otherwise the row says "Only after the plot is lapsed"). Final amount is edited with the pencil on its top block (Document status too). Payment status (old sheet) is no longer shown; Remaining balance replaces it, and it stays in Export all. DP can come in several instalments: "+ Add DP" saves a payment with `dpOf` = booking id (so it counts in Paid till now); the DP row shows the total and the list on hover (`dpEntries()` = DP typed on the booking + those payments). The Book step saves Booking amount/date/mode (`bookingAmount`…), not DP; `migrateBookingAmounts` moved older CRM bookings over.
- Forms: money boxes are numbers-only (`AMT_ATTR` / `amtHint()`: digits and one decimal point, ₹ amount shown under the box). "Book plot" form: Price (final amount, price per sq yd worked out) · Booking payment (amount, date, mode, note → the payment's note) · optional first DP (saved as a `dpOf` payment) · Loan (Bank, Loan amount, EMI only when "Loan Availed"; bank saved as `loanBank`) · live summary; refuses hold + booking + DP > final amount.
- **Paid till now — one rule everywhere** (`clientPaid(c, plot?)`, used by the folder blocks, per-plot view, Clients list, Book form and Data check): every received payment + the DP typed on a booking (pencil / old sheet, `dpAmount`) for the part the client's *other* payments don't already cover (other = not "Hold amount"/"Booking amount" entries and not `dpOf` DP payments), so old sheet bank lines that already contain the DP are not counted twice. Lapsed holds' typed DP is not counted. The folder's Payments table adds that part as a "From booking" row (`typedDpRows`), so its total = Paid till now. Never add up payments another way.
- **Lapse at any stage until MOU/dastavej** (owner's rule): a plot on hold, with DP, or booked can be lapsed (client backs out) until the MOU or dastavej is done (`docLock()` / `canLapse()`; server `lapseRefusal()` refuses it after that). Agents can lapse holds; only Admin/Super admin can lapse a booked plot (existing Booked lock). The Lapse form: date, reason, refund none / full (= everything paid for the plot) / part, refund amount/mode/date/note; shows what the company keeps. Lapsing frees the plot (status UNSOLD, plotOwners → '', booking Lapsed + `lapsedOn`/`lapseReason`). A refund is a payment with `kind: 'refund'`, `refundOf` = booking (positive amount, counted as money out via `signedAmt()`), shown −₹ in Payments; the Refund switch on a lapsed plot opens the same refund form. "Plots → Booking list" shows a lapsed plot as Available.
- **Payment modes**: Cash · UPI / Online (Online and UPI merged; `migratePayModes` updated saved data) · Cheque · NEFT · RTGS · Other. Each mode has its own proof boxes (`MODE_DETAILS` / `detailsFor()`), saved as `payName` / `payRef` / `payBank` on the payment (and on the booking for its booking payment): Cash = Received by / Receipt no.; UPI / Online = Transaction ID / UTR, UPI ID; Cheque = Cheque name / number / Bank name; NEFT/RTGS = UTR number / Bank name; Other = Details. Every mode box (`modeSel`, `data-mode`) shows its proof boxes underneath by itself (`renderDet`, read with `modeVals(id)`); the pencil does the same per record (`detGroups`) and empties them when the mode changes. Never show boxes of another mode (e.g. no cheque number for UPI). Payments table has a Details column. The pencil form groups booking fields under headings (`FIELD_SECTIONS`: Hold / Booking / Down payment (DP) / Refund / Loan) so hold and booking are never mixed up.
- **Built for daily use, not only the old sheets** (owner, Nov 2026): every module must let the team add new records going forward.
  - Site visits: "+ FU" in each row / "+ Add follow-up" on the visit page → tag FU1–FU4 (FU3 = Sahil Bhai, FU4 = Pratik Sir), date, note; appended to the Remark as "FU2 26/11/26: note" (`addFuText`); status becomes Follow up n (or Lapsed), except a visit in a non-lapsed client folder / a Booked visit keeps its status. A remark with no FU shows a grey "Visit" tag.
  - Agents: any agent box has "+ Add agent" (type a new name); agent lists are worked out live from visits/bookings/incentives (`allAgents()`).
  - Clients: `notes` collection (client, date, kind Payment call / Call / Meeting / Other, text, by). "+ Add remark" in the folder (Remarks table above Payments, with the hold remark) and "+ Remark" in the Clients list. The Clients list "Remark" is the LAST column = newest of the hold remark and these remarks (`clientRemark`). A payment's note is not a remark.
  - Contractors: "+ Add contractor"; "+ Add payment" on a contractor = ledger line. Contractor tags on expenses also match contractor names (`isConTag`). Expense form has Remarks.
  - Incentives: "+ Add incentive" from a booked plot; Final = Slab × (rate ÷ 5,750) × (size ÷ 200) − Advance, worked out live (`incFinal`). Booked plots since the first incentive row without a row are pointed out.
  - Sold plots: "+ Add to register" for a sold plot not in the Dastavej register. Land partner: "+ Add payment to Anjanee" adds to the plot's Anjanee paid and keeps the list (`anjaneePays`).
  - A plot booked in the CRM: "+ Add dastavej details" / "+ Add registry & maintenance" (client folder and plot page) create the record and open its pencil.
- Plots: TRPL plots and "Before TRPL" plots have separate Sr. series. Pratik is not shown in Incentives.
- Export (Excel/CSV, per list and "Export all") is Admin/Super admin only — files contain client phone numbers.
- Don't add file uploads yet (needs R2 + payment card). Don't add Meta/99acres/newsletters.

## How to work
1. Make the change locally.
2. Test: `npm install`, then `npm run db:local` (fresh local D1 from `data/seed.sql`) and `npm run dev` (http://localhost:8787), then `npm run test` (Playwright browser tests in `tests/`, all must pass; `__dbg` is a localhost-only hook the tests use). Add tests for new behaviour.
3. **Push straight to `main` yourself** as soon as all tests pass — don't wait for approval and don't use branches or pull requests (the owner wants every change on GitHub and live right away). Use clear commit messages; one commit per change.
4. About 1 minute after pushing, check the live site, then tell the owner in plain English what changed and where to see it.
Data fixes on live data go in the worker as a one-time migration guarded by a `meta` flag (see `migrateVisitRemarks`), never by editing data by hand.
